# EcoLink — превращаем отходы в доходы!

Платформа для команды **Enactus OshTU** (Кыргызстан): жители сёл продают вторсырьё, скупщики находят заявки,
объединяют небольшие партии в **коллективные сборы** и организуют выгодный вывоз. Пилот: **Кара-Суу**, Ошская область.

> **Это демонстрационная версия.** Тестовые данные помечены `DEMO`, SMS не отправляются, платежи не проводятся.

## Стек

Next.js (App Router) · TypeScript · Tailwind CSS · **PostgreSQL + Drizzle ORM / Drizzle Kit** · Leaflet + OpenStreetMap ·
React Hook Form + Zod · next-intl (RU / KG, EN — расширение) · Recharts · Vitest · Playwright.

Почему Drizzle, а не Prisma: в среде разработки был недоступен хост `binaries.prisma.sh`, поэтому Prisma CLI не запускался.
Слой данных переведён на Drizzle; Prisma из зависимостей удалена.

## Быстрый старт

Нужны Node.js 22+ и Docker (или своя PostgreSQL 16).

```bash
npm install
cp .env.example .env.local          # при необходимости измените значения
npm run db:up                       # PostgreSQL в Docker (создаёт базы ecolink и ecolink_test)
npm run db:migrate                  # применить SQL-миграции из ./drizzle
npm run db:seed                     # DEMO-данные для Кара-Суу
npm run dev                         # http://localhost:3000
```

Продакшен-режим: `npm run build && npm run start`.

> Примечание: в среде, где создавался проект, демон Docker был недоступен, поэтому `docker-compose.yml` проверен только на синтаксис
> (`docker compose config`); все проверки выполнялись на локальной PostgreSQL 16 с теми же миграциями.

Без Docker: создайте две базы (`ecolink`, `ecolink_test`), впишите строки подключения в `.env.local`.

## Роли и права

Проверка выполняется **на сервере**: в layout кабинета (`requirePage`) и в каждом server action / route handler (`requireActor`).

- **RESIDENT** — заявки, отмена, сравнение предложений, коллективные сборы, EcoWallet, подтверждение PIN, отзывы, споры.
- **BUYER** — карта и список заявок (без адресов и телефонов), принятие, планирование, маршрут, вес, цены, транспорт, аналитика, подписка (демо).
- **ADMIN** — пользователи, скупщики, заявки, сборы, категории, цены, подписки, бонусы, организации, споры, отзывы, настройки, журнал, CSV-экспорт.

## Как устроены ключевые механизмы

- **Принятие заявки** — один условный `UPDATE … WHERE status='AVAILABLE'` в транзакции + частичный уникальный индекс на активный забор.
  Из 6 одновременных скупщиков побеждает ровно один (тест).
- **Подтверждение передачи** — скупщик вводит фактический вес и получает одноразовый 6-значный PIN (в БД только SHA-256),
  срок 24 ч, 5 попыток. Житель вводит PIN → операция завершается, сумма = вес × согласованная цена (`Decimal`, не float).
- **EcoCoins** — начисляются только после подтверждения; уникальный индекс `(pickup, user, reason)` исключает двойное начисление.
- **Приватность** — публичные координаты смещены (≈ ±300 м); точный адрес, координаты и телефон видит только назначенный скупщик.
  В коллективном сборе показываются сокращённые имена и вес, без адресов.
- **Безопасность** — bcrypt, серверные сессии (в БД хеш токена, `httpOnly` cookie), блокировка после 5 неудачных входов,
  Zod-валидация, проверка файлов по сигнатуре, лимиты размера, защита CSV от формул, журнал действий, заголовки безопасности.
- **PWA** — manifest, иконки, service worker (кеширует только публичную статику и страницу «нет соединения»,
  HTML кабинетов не кешируется), индикатор связи, офлайн-черновики заявок с автосинхронизацией.

## Сценарий презентации Enactus

Автоматизирован в `e2e/enactus-demo.spec.ts` (все шаги меняют БД):

1. Открыть главную → 2. убедиться в слогане, кнопках и показателях из БД → 3. войти жителем → 4. создать заявку на 12 кг PET в Кара-Суу →
5. выбрать точку на карте → 6. сохранить → 7. войти скупщиком → 8. увидеть заявку → 9. принять → 10. открыть маршрут →
11. ввести фактический вес (получить PIN) → 12. житель вводит PIN → 13. операция завершена → 14. EcoCoins начислены (2/кг + 5) →
15. администратор видит статистику и журнал → 16. сбор «PET Кара-Суу» 85/100 кг, 12 участников → 17. переключить RU → KG.

Для живой демонстрации держите две вкладки (житель / скупщик в разных окнах или приватных режимах).

## Известные ограничения

- **Платежи и SMS не подключены.** Подписка — демо; «восстановление доступа» показывает код на экране (только вне production или с `DEMO_RESET_CODES=1`).
- **Коэффициенты CO₂ ориентировочные** и не подтверждены источником — см. `docs/CO2.md`. Заполните перед публичным использованием.
- **Цены в seed вымышлены**, не являются рыночными.
- **AI-распознавание отсутствует** (нет работающей модели); прогнозирование не реализовано. Вес по фото не определяется.
- **Маршруты** — только отображение точек и открытие во внешних картах; оптимизации и оценки расхода топлива нет.
  Таблицы `route_plans/route_stops` заполняются только seed.
- **Организации:** есть профиль, рейтинг по подтверждённому весу, ответственный (в БД); нет интерфейса назначения ответственного,
  отчётов и соревнований-мероприятий. Для детей персональные данные не собираются.
- **Администратор:** нет создания второго администратора в интерфейсе; нет редактирования спорных сумм вручную.
- **Фото** хранятся на диске (`.data/uploads`); для production нужно объектное хранилище.
- **Офлайн-черновики** лежат в `localStorage` без шифрования (без фото; удаляются при выходе). Если сеть оборвалась
  *после* создания заявки на сервере, но до ответа, возможен дубль — решается идемпотентным ключом (в планах).
- Плитки карты берутся с публичного `tile.openstreetmap.org`; для нагрузки нужен собственный тайл-сервер или провайдер.
- Ограничение частоты входа учитывается по номеру телефона (не по IP); общий rate-limit на регистрацию не реализован.
- EN-перевод — каркас (недостающие ключи берутся из RU).

## Деплой на Render

Категории сырья, бонусное правило и настройки создаются **не миграциями, а скриптом** `npm run db:bootstrap`
(безопасно запускать при каждом деплое: ничего не удаляет). Без него на пустой базе нет ни одной категории.

1. Создайте на Render **Blueprint** из репозитория (файл `render.yaml` создаст веб-сервис и PostgreSQL).
2. В Environment сервиса задайте `ADMIN_PHONE` (формат `+996XXXXXXXXX`) и `ADMIN_PASSWORD` (от 10 символов) — так создаётся администратор.
3. Старт выполняет `npm run start:prod` = миграции → bootstrap → `next start`.

Если сервис всё же запущен без bootstrap (например, командой `npm start`), базовые категории теперь создаются автоматически при первом открытии сайта.
Подключение к внешнему адресу базы Render (`*.render.com`) автоматически идёт по SSL.

Не запускайте `db:seed` в production: он очищает базу и создаёт DEMO-аккаунты с известным паролем.
